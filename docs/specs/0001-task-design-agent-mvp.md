# 과제 설계 에이전트 MVP

상태: ready-for-agent · 용어는 `GLOSSARY.md`, 결정 근거는 `docs/adr/0001`–`0003`을 따른다.

## Problem Statement

에이블제이 평가 서비스 담당자 2명은 AI 사용능력 평가 과제(상황·지시문·채점 기준)를 매번 처음부터 손으로 쓴다. 과제 1개에 평균 60분, 월 30개로 월 30시간이 든다. 지시문과 채점 기준이 서로 맞는지, 실제로 풀 수 있는지, 잘하는 응시자와 못하는 응시자를 가르는지는 담당자가 직접 풀어 보며 확인해야 해서, 시간이 들고 품질이 사람에 따라 흔들린다.

## Solution

담당자가 역량·대상자·목표 난이도를 입력하면 에이전트가 기존 과제를 참고해 상황 후보 3개를 제안한다. 담당자가 하나를 고르면 에이전트가 지시문, 첨부 자료(함정 포함), 채점 기준을 만들고, 상·중·하 응시자 페르소나로 모의 응시를 돌려 풀이 가능성, 변별력, 채점 일관성을 검증한다. 실패하면 해당 부분만 스스로 고친다. 담당자는 검증 결과가 붙은 초안을 받고, 다른 담당자가 최종 검토에서 검토 라벨을 붙여 확정 또는 반려한다. 시스템은 성공 기준을 직접 측정한다.

- 전면 재작성 없이 최종 검토를 통과한 초안 비율: 70% 이상
- 과제 1개당 총 작업 시간: 42분 이하

MVP의 목적은 핵심 흐름이 끝까지 실제로 동작하는 것과, 하이브리드 RAG, 멀티 에이전트, 중간 사람 확인, 자기 수정 루프, 로컬 + 클라우드 모델 라우팅 같은 에이전트 기법을 파이프라인의 실제 단계에서 쓰는 모습을 보여주는 것이다.

## User Stories

### 입력과 상황 설계

1. 담당자로서, 역량 체계에서 역량을 1~2개 골라 과제를 시작하고 싶다. 평가 목적에 맞는 과제를 만들기 위해서다.
2. 담당자로서, 대상자를 직무와 경력 수준으로 지정하고 싶다. 상황이 응시자 업무 맥락에 맞게 하기 위해서다.
3. 담당자로서, 목표 난이도(상·중·하)를 지정하고 싶다. 시험지 구성에 맞는 과제를 얻기 위해서다.
4. 담당자로서, 자유 메모를 선택적으로 덧붙이고 싶다. 정형 입력으로 표현할 수 없는 의도를 전하기 위해서다.
5. 담당자로서, 서로 충분히 다른 상황 후보 3개를 받고 싶다. 실제로 의미 있는 선택을 하기 위해서다.
6. 담당자로서, 각 상황 후보가 참고한 유사 과제를 보고 싶다. 후보가 어디서 영감을 받았는지 판단하기 위해서다.
7. 담당자로서, 기존 과제와 지나치게 비슷한 후보는 받고 싶지 않다. 과제 DB에 중복이 쌓이지 않게 하기 위해서다.
8. 담당자로서, 상황 후보 중 하나를 골라 다음 단계로 넘기고 싶다. 방향이 틀어지는 것을 가장 싼 시점에 바로잡기 위해서다.
9. 담당자로서, 마음에 드는 후보가 없으면 후보 3개를 다시 받고 싶다. 억지로 고르지 않기 위해서다.

### 생성

10. 담당자로서, 고른 상황에 맞는 지시문을 받고 싶다. 응시자가 할 일과 제출물을 명확히 하기 위해서다.
11. 담당자로서, 과제에 필요한 텍스트 첨부 자료(CSV, 메모, 이메일, 짧은 보고서)를 받고 싶다. 자료를 직접 만드는 시간을 줄이기 위해서다.
12. 담당자로서, 첨부 자료에 함정이 심겨 있고 그 위치가 표시되어 있기를 원한다. 응시자의 검증 행동을 평가하기 위해서다.
13. 담당자로서, 채점 기준이 항목 3~5개로 구성되고 각 항목에 역량, 배점, 0점·부분·만점 판정 기준이 있기를 원한다. 채점자 간 판단 차이를 줄이기 위해서다.
14. 담당자로서, 채점 기준에 과정 항목이 반드시 1개 이상 있기를 원한다. 산출물만 좋은 하 수준 응시자가 고득점하지 않게 하기 위해서다.
15. 담당자로서, 검토 에이전트가 지시문과 채점 기준의 정합성을 미리 점검하기를 원한다. 모의 응시 전에 명백한 불일치를 걸러내기 위해서다.
16. 담당자로서, 모든 초안이 같은 구조로 나오기를 원한다. 검토와 저장을 일관되게 하기 위해서다.

### 모의 응시와 검증

17. 담당자로서, 상·중·하 응시자 페르소나가 AI 도구 LLM을 써서 과제를 실제로 푸는 모습을 원한다. 과제가 풀리는지 직접 풀지 않고 확인하기 위해서다.
18. 담당자로서, 페르소나 수준이 모델 성능이 아니라 AI 사용 행동으로 구분되기를 원한다. 측정 대상인 사람의 AI 사용능력을 흉내 내기 위해서다.
19. 담당자로서, 각 페르소나의 AI 도구 대화 기록과 최종 산출물을 열어 보고 싶다. 점수가 왜 그렇게 나왔는지 이해하기 위해서다.
20. 담당자로서, 상 수준 페르소나가 70점 이상인지(풀이 가능성) 알고 싶다. 풀 수 없는 과제를 내보내지 않기 위해서다.
21. 담당자로서, 점수가 상 > 중 > 하 순서이고 상·하 차이가 30점 이상인지(변별력) 알고 싶다. 과제가 능력 차이를 잡아내는지 확인하기 위해서다.
22. 담당자로서, 같은 제출물을 3회 채점했을 때 표준편차가 5점 이하인지(채점 일관성) 알고 싶다. 채점 기준이 모호하지 않은지 확인하기 위해서다.
23. 담당자로서, 검증 판정 기준값을 설정에서 조정하고 싶다. 운영하면서 기준을 보정하기 위해서다.

### 자기 수정 루프

24. 담당자로서, 풀이 불가로 판정되면 에이전트가 지시문을 고치기를 원한다. 원인에 맞는 부분만 손대기 위해서다.
25. 담당자로서, 변별력 부족으로 판정되면 에이전트가 채점 기준이나 함정을 고치기를 원한다. 능력 차이가 점수에 드러나게 하기 위해서다.
26. 담당자로서, 채점 불일치로 판정되면 에이전트가 채점 기준의 판정 서술을 고치기를 원한다. 모호함을 없애기 위해서다.
27. 담당자로서, 내가 고른 상황은 자기 수정 루프가 바꾸지 않기를 원한다. 내 결정이 존중되게 하기 위해서다.
28. 담당자로서, 자기 수정 루프가 최대 3회 또는 토큰 예산에서 멈추기를 원한다. 비용과 대기 시간이 끝없이 늘지 않게 하기 위해서다.
29. 담당자로서, 끝내 검증에 실패한 초안도 실패 리포트와 함께 받고 싶다. 직접 고쳐 쓸지 판단하기 위해서다.
30. 담당자로서, 수정 회차별로 무엇이 왜 바뀌었는지 보고 싶다. 에이전트의 판단을 신뢰할 수 있는지 판단하기 위해서다.

### 진행 상황

31. 담당자로서, 에이전트가 지금 어느 단계에 있는지 실시간으로 보고 싶다. 기다리는 동안 상황을 파악하기 위해서다.
32. 담당자로서, 세 페르소나가 병렬로 응시하는 모습을 보고 싶다. 대기 시간이 왜 그만큼인지 이해하기 위해서다.
33. 담당자로서, 화면을 닫았다가 돌아와도 진행 중인 초안을 이어서 보고 싶다. 긴 실행 중에 다른 일을 하기 위해서다.

### 최종 검토

34. 검토자로서, 상황·지시문·첨부 자료·채점 기준을 한 화면에서 편집하고 싶다. 고칠 부분을 바로 고치기 위해서다.
35. 검토자로서, 모의 응시 점수표와 실패 리포트를 편집 화면 옆에서 보고 싶다. 근거를 보며 판단하기 위해서다.
36. 검토자로서, 상황·지시문·채점 기준 각각에 검토 라벨(유지 / 부분 수정 / 전면 재작성)을 붙이고 싶다. 성공 기준을 측정하기 위해서다.
37. 검토자로서, 라벨을 다 붙여야만 확정이나 반려를 할 수 있기를 원한다. 지표에 빈칸이 생기지 않게 하기 위해서다.
38. 담당자로서, 내가 작성한 초안은 내가 최종 검토를 할 수 없기를 원한다. 교차 검토 원칙을 지키기 위해서다.
39. 담당자로서, 로그인 없이 화면 상단에서 담당자 2명 중 나를 고르고 싶다. MVP에서 인증 부담 없이 역할을 구분하기 위해서다.
40. 검토자로서, 확정된 과제가 과제 DB에 들어가 이후 유사 과제 검색에 쓰이기를 원한다. 쓸수록 참고 예시가 좋아지게 하기 위해서다.
41. 검토자로서, 반려된 초안도 검토 라벨과 함께 남기를 원한다. 실패 패턴을 분석하기 위해서다.

### 측정과 대시보드

42. 담당자로서, 전면 재작성 없이 통과한 비율을 대시보드에서 보고 싶다. 성공 기준 70% 달성 여부를 판단하기 위해서다.
43. 담당자로서, 과제 1개당 총 작업 시간(사람 시간 + 에이전트 대기 시간)을 보고 싶다. 42분 목표와 비교하기 위해서다.
44. 담당자로서, 사람 시간에서 탭 비활성 시간은 빠지기를 원한다. 실제 작업 시간만 재기 위해서다.
45. 담당자로서, 구성요소별 검토 라벨 분포를 보고 싶다. 어느 부분이 가장 자주 다시 쓰이는지 알기 위해서다.
46. 담당자로서, 과제별 LLM 비용과 호출 수를 보고 싶다. 운영 비용을 예측하기 위해서다.
47. 담당자로서, 각 실행의 단계별 추적(프롬프트, 응답, 지연)을 열어 보고 싶다. 품질 문제를 디버깅하기 위해서다.

### 데이터와 시연

48. 개발자로서, 합성 역량 체계(역량 약 8개, 하위 요소, 상·중·하 수준 지표)를 시드하고 싶다. 실제 데이터 없이 시스템을 돌리기 위해서다.
49. 개발자로서, 합성 과제 약 30개와 채점 기준을 과제 DB에 시드하고 싶다. 유사 과제 검색이 처음부터 동작하게 하기 위해서다.
50. 개발자로서, 실제 데이터가 생기면 같은 구조로 교체하고 싶다. 시드 데이터에 묶이지 않기 위해서다.
51. 개발자로서, 입력 조합 10~15개로 과제를 일괄 생성하는 명령을 원한다. 시연용 지표를 채우기 위해서다.
52. 개발자로서, 명령 하나로 앱, DB, 추적 도구를 로컬에서 띄우고 싶다. 누구나 같은 환경으로 시연하기 위해서다.
53. 개발자로서, 로컬 LLM 엔드포인트가 없을 때 응시자 페르소나와 AI 도구 LLM을 Gemini로 돌리는 스위치를 원한다. `ml` 서버 없이도 끝까지 시연하기 위해서다.
54. 아바타 운영자로서, 과제 설계 에이전트의 로컬 LLM이 아바타 생성의 메모리와 지연에 영향을 주지 않기를 원한다. 프로덕션 서비스 품질을 지키기 위해서다.

## Implementation Decisions

### 모듈

- **과제 설계 서비스**: 화면이 호출하는 유일한 진입점이자 테스트 경계다. 연산은 다음과 같다.
  - `start(입력, 작성자)`: 상황 후보 3개를 만들고, 초안을 `상황 선택 대기` 상태로 둔다.
  - `regenerate_scenarios(초안)`: 상황 후보를 다시 받는다.
  - `select_scenario(초안, 후보)`: 생성, 모의 응시, 자기 수정 루프를 실행하고 초안을 `검토 대기` 상태로 둔다.
  - `get_draft(초안)`: 초안의 현재 상태, 회차별 이력, 모의 응시 결과를 돌려준다.
  - `review(초안, 검토자, 검토 라벨, 수정본)`: 초안을 확정 또는 반려한다.
  - `metrics(기간)`: 대시보드 지표를 계산한다.
  - `record_activity(초안, 담당자, 활성 구간)`: 사람 시간을 기록한다.
- **워크플로우**: LangGraph 상태 그래프로 만든다.
  - 노드 순서: 유사 과제 검색 → 상황 후보 생성과 중복 검사 → 중간 사람 확인(interrupt) → 지시문 작성 → 첨부 자료 작성 → 채점 기준 작성 → 검토 에이전트 → 모의 응시(세 페르소나 병렬) → 채점(제출물마다 3회) → 판정 → 실패 유형에 따른 수정 노드 또는 종료.
  - 체크포인트를 Postgres에 저장해 중단된 실행을 재개할 수 있게 한다.
- **모델 게이트웨이**: 역할 단위 인터페이스 하나로 모든 모델 호출을 감싼다. 역할은 생성, 검토, 응시자 페르소나, AI 도구, 채점, 리랭크, 임베딩이다.
  - 역할별로 공급자, 모델 ID, thinking level, 토큰 예산을 설정으로 매핑한다.
  - 모든 출력은 JSON 스키마로 검증하고, 형식이 맞지 않으면 재시도한다.
  - 호출마다 토큰과 비용을 초안 단위로 누적한다.
- **과제 저장소**: Postgres에 pgvector와 pg_trgm 확장을 쓴다.
  - 하이브리드 검색: 트라이그램 유사도(키워드 쪽, 한국어 형태소 문제를 우회)와 벡터 유사도를 RRF로 합친 뒤, 상위 후보를 LLM 리랭커로 다시 정렬한다.
  - 중복 검사: 임베딩 코사인 유사도 0.85 이상이면 중복으로 본다. 값은 설정에서 바꿀 수 있다.
- **역량 체계 저장소**: 역량 → 하위 요소 → 수준 지표를 읽기 전용으로 조회한다. 페르소나 프롬프트와 채점 기준의 역량 연결에 쓴다.
- **측정**: 사람 활성 구간, 에이전트 실행 구간, 검토 라벨, 비용을 기록하고 지표를 계산한다.
- **화면**: Streamlit 5개 화면(입력 폼, 상황 후보 선택, 진행, 검토, 대시보드)과 상단 담당자 선택. 화면은 과제 설계 서비스만 호출한다.
- **시드와 일괄 생성**: 합성 역량 체계와 과제를 생성해 적재하는 명령, 그리고 입력 조합 목록으로 과제를 일괄 생성하는 명령.
- **추적**: Langfuse로 실행 단위 추적과 비용을 기록한다.

### 모델 라우팅

| 역할 | 기본 공급자 |
|---|---|
| 생성, 검토 에이전트, 채점, 리랭크 | Gemini 3.8 Flash, thinking high |
| 응시자 페르소나, AI 도구 LLM | 로컬 Qwen3.8-27B 4bit (`ml` 서버 vLLM, OpenAI 호환 API) |
| 임베딩 | Gemini 임베딩 모델 |

- 정확한 모델 ID는 설정으로만 지정한다. "3.8 Flash"의 실제 API ID는 확인이 필요하다.
- 로컬 엔드포인트를 쓸 수 없으면 설정 스위치로 응시자 페르소나와 AI 도구 LLM을 Gemini로 돌린다.
- 로컬 LLM은 SSH 터널(jump 경유)로 접근한다.
- `ml` 서버 운영 제약(ADR 0003):
  - GPU 1장만 쓴다.
  - vLLM 메모리 비율은 약 0.35로 둔다.
  - MPS로 연산 비율을 약 30%로 제한한다.
  - 아바타 생성 중 최대 메모리를 실측하기 전에는 배포하지 않는다.

### 모의 응시 (ADR 0001)

- 세 페르소나는 같은 모델을 쓰고, 해당 역량의 수준 지표를 프롬프트로 주입받아 행동만 다르다.
  - 하: 지시문을 그대로 붙여넣고 첫 출력을 바로 제출한다.
  - 중: 맥락과 형식을 지정하고 1~2회 고쳐 요청한다.
  - 상: 작업을 쪼개 요청하고, 사실과 함정을 확인하고, 반복 개선한다.
- 페르소나와 AI 도구 LLM은 최대 6턴까지 대화한다. 제출물은 대화 기록과 최종 산출물이다.
- 채점 에이전트는 제출물마다 3회 독립적으로 채점한다. 항목별 점수와 근거를 남긴다.

### 판정과 자기 수정

- 판정 기준값(설정에서 조정 가능):
  - 풀이 가능성: 상 수준 점수 70점 이상
  - 변별력: 상 > 중 > 하이고, 상과 하의 차이가 30점 이상
  - 채점 일관성: 3회 채점 표준편차 5점 이하
- 실패 유형별 수정 대상:
  - 풀이 불가 → 지시문
  - 변별력 부족 → 채점 기준 또는 함정
  - 채점 불일치 → 채점 기준의 판정 서술
  - 여러 유형이 동시에 실패하면 이 순서대로 하나씩 처리한다.
  - 상황은 수정 대상이 아니다.
- 최대 3회, 또는 초안별 토큰 예산을 넘으면 중단한다. 이때 실패 리포트(실패 유형, 회차별 점수, 시도한 수정)를 붙여 `검토 대기`로 넘긴다.

### 데이터 구조

- **초안 상태**: `생성 중` → `상황 선택 대기` → `검증 중` → `검토 대기` → `확정` | `반려`
- **과제**: 상황, 지시문, 첨부 자료 목록(파일명, 형식, 내용, 함정 표시), 채점 기준, 연결 역량, 대상자, 목표 난이도, 임베딩
- **채점 기준 항목**: 역량 ID, 유형(과정 / 산출물), 배점, 0점·부분·만점 판정 기준. 과정 항목은 1개 이상이어야 한다.
- **초안 회차**: 회차 번호, 변경된 구성요소, 변경 사유, 해당 회차의 모의 응시 결과
- **모의 응시 결과**: 페르소나 수준, 대화 기록, 산출물, 3회 채점 점수와 근거
- **검토**: 검토자, 구성요소별 검토 라벨, 확정 또는 반려, 수정본
- **측정 이벤트**: 담당자, 초안, 구간 종류(사람 활성 / 에이전트 실행), 시작과 끝
- **비용**: 초안별 역할별 토큰, 호출 수, 추정 비용
- **담당자**: 2명을 고정으로 등록한다. 초안의 작성자와 같은 사람은 검토할 수 없다.

### 실행 환경

- 앱, Postgres(pgvector), Langfuse는 docker-compose로 로컬에서 띄운다.
- 로컬 LLM만 `ml` 서버에서 실행한다.
- 언어는 Python이고, 모든 과제 콘텐츠는 한국어다.

## Testing Decisions

- **테스트 경계는 과제 설계 서비스 하나다.** 테스트는 공개 연산(`start`, `select_scenario`, `review`, `metrics` 등)으로 외부 동작만 검증한다. LangGraph 노드, 개별 에이전트, 프롬프트 문자열은 직접 테스트하지 않는다.
- **환경**:
  - 모델 게이트웨이는 가짜로 바꾼다. 역할별로 정해진 응답(생성물, 페르소나 대화, 채점 점수, 임베딩 벡터, 리랭크 순서)을 돌려준다.
  - Postgres는 실제 인스턴스(pgvector, pg_trgm 포함)를 쓴다.
- **좋은 테스트의 기준**: 담당자가 관찰할 수 있는 결과를 확인한다. 예를 들어 초안 상태, 반환된 후보 수, 검증 판정, 실패 리포트 내용, 확정 과제의 검색 노출, 지표 값이다. 내부 구조를 바꿔도 깨지지 않아야 한다.
- **다룰 시나리오**:
  - 정상 흐름: 입력 → 후보 3개 → 선택 → 첫 회차 통과 → 검토 대기 → 검토 라벨 → 확정 → 유사 과제 검색에 노출
  - 실패 유형별로 올바른 구성요소만 바뀌고 상황은 그대로인지
  - 3회 실패, 또는 토큰 예산 초과 시 실패 리포트를 붙여 검토 대기로 가는지
  - 중복 임계값을 넘는 후보가 다시 생성되는지
  - 하이브리드 검색이 키워드 일치와 의미 일치를 모두 찾는지
  - 작성자 본인 검토가 거부되는지, 검토 라벨이 빠진 검토가 거부되는지
  - 지표 계산: 전면 재작성 비율, 비활성 시간을 뺀 총 작업 시간, 비용 합계
  - 로컬 LLM 스위치가 꺼지면 페르소나 역할이 Gemini 공급자로 라우팅되는지
  - 체크포인트에서 재개해도 같은 결과가 나오는지
- **수동 품질 검증**(자동 테스트 아님): 일괄 생성으로 과제 10~15개를 만들고, 사람이 검토 라벨을 붙여 실제 지표를 확인한다(ADR 0002). 로컬 모델의 한국어 페르소나 품질을 표본으로 확인한다.
- **기존 사례**: 저장소가 비어 있어 따를 기존 테스트가 없다. 이 스펙의 테스트가 기준이 된다.

## Out of Scope

- 로그인과 권한 관리. 상단 담당자 선택으로 대체한다.
- 이미지, PDF 첨부 자료
- 실제 에이블제이 역량 체계와 과제 데이터 연동. 같은 구조의 합성 데이터로 대체한다.
- 실제 응시자에게 과제를 배포하거나 실제 응시 결과를 받는 기능
- 검토 라벨의 LLM 자동화(ADR 0002)
- 앱 자체의 프로덕션 배포. 로컬 docker-compose만 지원한다.
- 로컬 모델 파인튜닝, GPU 분할(MIG 미지원 장비)
- 실제 사람 응시자와 페르소나 점수 사이의 상관 검증

## Further Notes

- "Gemini 3.8 Flash"와 "Qwen3.8-27B"의 정확한 모델 ID와 제공 형태(4bit 양자화본 존재 여부)는 구현 첫 단계에서 확인한다.
- Qwen3.8-27B의 한국어 성능은 공개 벤치마크로 확인되지 않았다. 응시자 페르소나 품질이 부족하면 스위치로 Gemini에 되돌린다.
- 로컬 모델 라이선스를 확인한다(Apache 2.0으로 알려짐). EXAONE은 비상업 라이선스 우려로 제외했다.
- 생성과 채점이 같은 Gemini 모델이라 자기 평가 편향이 남는다. 채점 에이전트 공급자를 바꿀 수 있게 설정을 열어 둔다.
- `ml` 배포 전에 아바타 담당자와 협의하고, 아바타 세션 중 최대 GPU 메모리를 측정한다. 현재 측정치는 GPU당 약 19.4GB 사용 중이고, 측정 시점의 사용률은 0%다.
- 총 작업 시간에 에이전트 대기 시간이 들어가므로, 모의 응시 병렬화와 역할별 thinking level 조정이 42분 목표를 맞추는 주요 수단이다.
